# Pass H — Modern DS Remaster Visual Design

Status: **LOCKED DESIGN DIRECTION / implementation pending**

## Purpose

Pass H is the second-generation visual overhaul for this project.

Pass G proved that Platinum can be pushed substantially through native DS resource and rendering paths:
- modernized shared UI chrome;
- stronger battle-healthbox presentation;
- richer battle-terrain palettes;
- selective move-impact staging;
- field lighting/fog/camera improvements;
- environment-specific palette/material grading;
- source-backed visual generators and validation.

Pass H deliberately goes further.

The new target is **not** “retail Platinum, polished.” It is:

> **A modern, intense, immersive Pokémon experience that is still a real Nintendo DS ROM and is designed to look excellent when played through a DS emulator on an iPhone.**

Platinum remains the engine, map, content, and gameplay base. Its 2009 retail presentation is no longer a visual constraint.

The user explicitly wants the project to be willing to stray from authentic Platinum presentation when that produces a stronger modern result.

---

## Runtime target

Primary user runtime:
- Nintendo DS emulator on iPhone;
- both landscape side-by-side and portrait stacked screen layouts;
- touch input on the DS bottom screen;
- emulator control overlays may partially overlap the rendered screens;
- no external texture packs;
- no emulator-specific shaders;
- no emulator skin dependency;
- no post-processing dependency.

The game must remain a self-contained ROM-side visual overhaul.

### Hard DS constraints

Every design decision must respect:
- 256x192 pixels per DS screen;
- indexed/paletted Nitro 2D resource contracts where applicable;
- existing NCGR/NCLR/NCER/NANR/NSCR resource assumptions unless a deliberate source change expands them;
- VRAM/OAM and palette limits;
- dual-screen composition;
- touch-screen interaction model;
- existing save/gameplay behavior;
- normal US Rev 0 and Rev 1 build compatibility.

Modernization must come from:
- stronger composition;
- richer pixel art;
- cleaner palette hierarchy;
- deliberate contrast;
- better visual states;
- sharper motion language;
- better atmosphere;
- more dramatic staging;
- selective source-backed layout changes.

It must **not** depend on native-iOS UI conventions that collapse at DS resolution.

---

# Visual identity

## Working identity

**Pokémon Platinum — Modern DS Remaster**

The visual language should feel like a premium late-generation DS game that never existed rather than a mobile-app skin pasted over Platinum.

### Three pillars

1. **Premium clarity**
   - readable at phone scale;
   - crisp hierarchy;
   - fewer muddy beige/gray surfaces;
   - fewer decorative elements that consume pixels without communicating state.

2. **Battle intensity**
   - battles should feel like confrontations;
   - important actions should have anticipation, impact, and recovery;
   - bosses, rivals, Gym Leaders, Elite Four, Champion, Galactic commanders, and Legendary encounters should feel more consequential than ordinary encounters.

3. **Atmospheric Sinnoh**
   - exploration keeps recognizable Sinnoh geography;
   - environments can be substantially moodier, colder, darker, warmer, richer, or more stylized than retail;
   - weather, lighting, palettes, camera framing, and environment-specific UI presentation should reinforce place.

# Global art-direction rules

## 1. Pixel-first, not app-first

The interface may feel modern, but it must still be authored for DS pixel density.

Prefer:
- 1-3 px borders with clear hierarchy;
- controlled bevels and inset highlights;
- intentional 4bpp ramps;
- strong silhouette;
- readable icons;
- broad value separation.

Avoid:
- ultra-thin lines;
- subtle low-contrast gradients;
- tiny icons;
- glassmorphism;
- excessive transparency;
- smartphone-style text density;
- decorative detail that disappears at 256x192.

## 2. Dark-neutral chassis + contextual color

The UI chassis should use a coherent dark-neutral family:
- near-black navy;
- graphite;
- steel/slate;
- cool white;
- restrained silver highlights.

Contextual color should communicate state:
- Fight / offense: crimson-red;
- Bag / inventory: amber-gold;
- Pokémon / party: green;
- Run / retreat: cyan-blue;
- selected/focus: bright white + electric-blue or warm-gold edge;
- disabled/unavailable: desaturated graphite;
- danger/low HP: saturated red/orange;
- status conditions: preserve strong canonical differentiation.

The result should be less toy-like than the retail four-color command screen while preserving immediate recognition.

## 3. Screen-edge safety

Because iPhone emulator controls can overlap edges, essential information should not rely on the outermost 8 px of the bottom screen where avoidable.

This is not an emulator-specific layout fork. It is a safe-area design preference:
- critical labels centered inside touch targets;
- state indicators inset;
- no tiny confirm prompts placed only in corners;
- no important readout that requires an unobstructed extreme edge.

## 4. Motion hierarchy

Motion should communicate importance.

Three tiers:

### Tier 1 — ambient
- 2-6 px drift;
- subtle pulse;
- restrained cursor bounce;
- environmental motion;
- no screen-wide shake.

### Tier 2 — action
- short panel flash;
- button compression;
- small arena jolt;
- strong cursor/state response;
- 2-6 frames of emphasis.

### Tier 3 — climax
Reserved for:
- critical battle moments;
- boss introductions;
- Legendary encounters;
- heavy attacks;
- victory/faint transitions where technically safe.

May use:
- stronger fade/grade;
- synchronized background reaction;
- more deliberate timing;
- selective screen-wide motion.

Do not normalize Tier 3 behavior across ordinary actions.

## 5. Contrast target

At emulator phone scale:
- important text must remain readable without zoom;
- active controls must be visually obvious in a still screenshot;
- HP state must be recognized instantly;
- type/category identity must not rely on text alone;
- night scenes must remain navigable;
- snow/fog scenes must preserve player and terrain separation.

# Battle presentation design

Battle is the highest-priority Pass H surface.

The intended split is:

> **Top screen = cinematic confrontation.**
>
> **Bottom screen = tactile command center.**

## H1A — top-screen battle HUD

### Healthboxes

Retain the Pass G navy/slate direction but move from “recolored retail frame” toward a more authored modern HUD.

Design:
- thinner outer silhouette where geometry permits;
- stronger dark outline;
- cleaner name/level grouping;
- clearer HP rail;
- intentional empty-space control;
- player/enemy boxes visually related but not identical;
- doubles layout must remain readable;
- Safari healthbox receives its own compatible treatment instead of remaining an obvious retail holdout.

HP behavior:
- green/yellow/red remain canonical;
- low HP should receive stronger visual urgency through frame accent or pulse only if source-safe;
- do not change gameplay timing or HP-depletion logic.

Status:
- preserve canonical status readability;
- optional compact status badge treatment if the existing renderer permits it without sacrificing text space.

### Dialogue box

The current large pale retail-style battle message box is a major remaining 2009 visual cue.

Target:
- darker or cool-neutral frame;
- less beige;
- cleaner high-contrast interior;
- stronger separation from the battle scene;
- keep text readability first;
- retain printer timing and message behavior.

Do not reduce message capacity or create text overflow.

## H1B — bottom-screen command screen

Current retail composition is recognizable but visually dated:
- large bright beveled rectangles;
- pale-green background;
- heavy black bevels;
- limited state differentiation beyond color.

Target:
- retain four-action touch usability;
- reduce visual bulk;
- create a more deliberate command deck;
- make FIGHT dominant without wasting half the screen;
- keep Bag / Run / Pokémon quickly reachable;
- keep labels centered and clear under emulator overlays.

### Required states

Every command control must have:
- idle;
- focused/selected;
- pressed/confirmed where the engine exposes a state;
- disabled where applicable.

The selected state must be visible without relying only on the existing red corner cursor.

### Direction

Recommended composition:
- FIGHT remains the primary large action;
- Bag, Pokémon, and Run remain secondary;
- background becomes dark-neutral/steel rather than pale retail green;
- each action keeps a recognizable accent color;
- icon + wordmark pairing preferred when the resource contract permits;
- use inset highlight / inner shadow rather than thick 2009 bevel.

The exact geometry must be source-audited before layout changes. If the command menu is resource-locked, achieve the visual hierarchy through art/palette first and then make only proven layout/code changes.

## H1C — move selection screen

The move screen should feel like four **action cards**, not four blank DS menu cells.

Each populated move target should clearly communicate:
- move name;
- type;
- PP current/max;
- physical/special/status category if a source-backed placement can be added safely;
- selection state.

Desired hierarchy:
1. move name;
2. type/category;
3. PP;
4. decorative chrome.

Recommended visual behavior:
- card background derives subtly from move type, but text remains high contrast;
- selected card gains a bright edge and/or stronger value lift;
- empty slots remain intentionally dark/quiet;
- Cancel is visually subordinate;
- avoid oversaturated full-card type colors that make four cards visually noisy.

If category icons cannot be added without intrusive runtime changes, defer them rather than faking them into move names or type text.

## H1D — battle scene intensity

Retain all G5 work.

Expand only where payoff is high:
- enemy/player entrance staging;
- trainer battle opening;
- boss/rival/Gym/Elite/Champion encounter grade;
- Legendary encounter grade;
- faint/KO punctuation;
- critical hit presentation;
- super-effective / resisted visual feedback;
- victory transition polish.

Rules:
- no global shake on every hit;
- no long animation tax on routine encounters;
- no change to battle mechanics;
- no particle spam;
- no frame-pacing regressions.

The existing G5 scene-grade and `Func_ShakeBg` language is the foundation.

# Encounter-class presentation

Pass H should create stronger visual hierarchy between encounter types.

## Ordinary wild
- fastest presentation;
- terrain/time-of-day identity;
- minimal extra ceremony.

## Ordinary trainer
- slightly stronger intro framing;
- trainer identity should read cleanly;
- no boss-grade effects.

## Rival
- distinct rivalry accent;
- faster, energetic transition;
- stronger start beat than ordinary trainers.

## Gym Leader
- leader-specific or Gym-class visual grade;
- stronger intro;
- badge-era progression should feel consequential.

## Galactic Commander / Cyrus
- colder industrial/violet identity;
- sharper transition;
- stronger contrast and tension.

## Elite Four
- preserve member-specific arena identities already introduced in G5;
- stronger entrance beat;
- restrained premium framing rather than excessive particles.

## Champion
- pearl/lavender/charcoal identity;
- highest ordinary-trainer presentation tier;
- cinematic but readable.

## Legendary / Mythical
- encounter-specific atmosphere where practical;
- use field transition + battle grade + existing animation systems;
- avoid one generic “legendary effect” for all species;
- flagship encounters may receive custom timing if source-safe.

# Core menu design

## H2A — Start menu

Target:
- cleaner icon silhouettes;
- stronger selected state;
- dark-neutral chassis;
- less retail beige/gray;
- maintain one-glance function recognition.

Do not change menu function ordering unless a separate UX case is explicitly approved.

## H2B — Party menu

Pass G already modernized cursor/button chrome.

Pass H target:
- stronger member-card hierarchy;
- easier HP/status scanning;
- selected Pokémon should read immediately;
- touch controls should look intentionally interactive;
- empty party positions should be quiet;
- avoid over-framing every element.

Where possible:
- separate name/level from HP/status through value hierarchy;
- strengthen Pokémon icon presentation;
- keep held-item/status indicators readable.

## H2C — Pokémon Summary

This should become one of the project's showcase UI systems.

Target:
- modern tab treatment;
- cleaner page identity;
- better visual grouping for stats/moves/ability/type;
- stronger move-card treatment consistent with battle;
- clearer selection cursor;
- preserve all existing information.

Do not simplify by removing data.

## H2D — Bag

Target:
- clearer pocket identity;
- stronger selected-item row;
- cleaner item-count/value hierarchy;
- less flat/washed background;
- maintain quick scrolling and touch behavior.

## H2E — Shop / transaction UI

Target:
- visually match Bag;
- clear money/cost emphasis;
- obvious selected row;
- consistent button/cursor language.

## H2F — Pokédex / PC / miscellaneous high-frequency menus

These are second-wave systems.

They should be audited after the battle + party + summary + bag foundation is stable.

The goal is coherent visual language, not mandatory layout rewrites.

# Overworld presentation design

Pass G already upgraded showcase environments. Pass H should expand the **experience-wide atmosphere**, not simply recolor every map.

## H3A — regional color language

Define broad Sinnoh families:
- temperate route: cool greens + blue atmospheric depth;
- forest: deep emerald / blue-green shadow;
- mountain: desaturated slate / cold stone;
- snow: blue-white / lavender shadow;
- coast: cyan depth + cleaner sand/rock separation;
- urban: cooler neutrals with city-specific accents;
- Galactic: steel / cyan / violet;
- ancient/legendary: restrained high-contrast specialty grades;
- Distortion: black-violet / magenta / electric-blue accent.

Do not force all maps in a family to identical palettes.

## H3B — time of day

Strengthen dawn/day/evening/night separation where existing lighting architecture supports it.

Night should be:
- darker;
- cooler;
- richer;
- still navigable.

Do not solve “night” by uniformly reducing brightness.

## H3C — environmental motion

Prefer native systems already proven in Pass G:
- weather;
- fog;
- field effects;
- billboard renderers;
- map-prop animation.

Add new ambient effects only if:
- resource ownership is understood;
- allocation is bounded;
- effect density is conservative;
- cleanup is proven;
- dual-revision builds stay green.

## H3D — camera framing

Use bespoke camera profiles only in areas where composition benefits materially.

Avoid changing camera behavior globally.

Showcase candidates:
- dramatic summit/legendary spaces;
- forests;
- select city entrances;
- Distortion World;
- League/Champion approach.

Navigation readability wins over cinematic framing.

---

# Transition design

Transitions are one of the strongest ways to reduce the “2009 DS” feeling without rebuilding whole screens.

Targets:
- battle entry;
- trainer-class entry;
- menu open/close;
- major-area entry;
- important item/reward moments;
- faint/victory where source-safe.

Direction:
- short;
- crisp;
- purposeful;
- no long unskippable flourish for routine actions.

Preferred techniques:
- palette fade;
- brief wipe;
- sprite/panel slide;
- contextual flash;
- existing transition systems;
- existing battle staging primitives.

Avoid:
- expensive full-screen compositing systems unless a source audit proves the payoff.

---

# Typography and information density

Do not replace the entire font system unless there is a proven, build-safe reason.

The modern feel should primarily come from:
- better frames;
- better spacing;
- stronger value hierarchy;
- shorter visual scan paths;
- clearer icons;
- better panel contrast.

If font work is attempted:
- preserve every glyph needed by the game;
- preserve text-width assumptions or audit them comprehensively;
- validate line wrapping;
- validate names, long move names, item names, trainer names, Pokédex entries, and multi-line dialogue.

Typography changes are **not** an H1 blocker.

---

# Sprite philosophy

Pass H does not require replacing all Pokémon or trainer sprites.

Use:
- existing Pass G audits;
- HGSS where a compatible asset is clearly superior;
- Platinum-native sprites when they remain the strongest fit.

The modern feel should not depend on mass sprite replacement.

If a sprite is changed:
- preserve species/trainer identity;
- maintain palette correctness;
- preserve animation/cell contracts;
- validate shiny/alternate forms where applicable.

---

# Intensity without visual fatigue

The project should feel more intense, not exhausting.

### Escalation rule

The game should visibly escalate:

ordinary field < ordinary wild < ordinary trainer < rival/Galactic < Gym < Elite Four < Champion/flagship Legendary

If every screen constantly uses:
- maximum saturation;
- maximum shake;
- maximum particles;
- maximum contrast;

then nothing feels important.

Use restraint at the low end so the high end has somewhere to go.

---

# Emulator-oriented acceptance criteria

Every completed H-phase visual system should be reviewed under:

## Portrait / stacked
- both DS screens visible vertically;
- touch screen physically larger;
- control overlay present;
- no critical information hidden by common overlay regions;
- bottom-screen touch targets remain obvious.

## Landscape / side-by-side
- each DS screen physically smaller;
- small text remains legible;
- selected states remain obvious;
- type/HP/status colors do not collapse;
- large empty UI areas do not dominate the composition.

## Image scaling
The design should survive normal emulator scaling without relying on:
- CRT filters;
- integer-only scaling;
- smoothing;
- custom shaders.

---

# Non-goals

Pass H does not:
- change battle mechanics;
- change Pokémon balance;
- change learnsets;
- alter encounter balance;
- change story progression;
- require emulator code;
- require a texture pack;
- convert Platinum into a native iOS application;
- replace the DS renderer wholesale;
- discard Pass G work;
- pursue “authentic 2009 Platinum” as a design objective.

---

# Quality bar

A Pass H screen is successful when:
- it is immediately recognizable as Pokémon;
- it is clearly more modern than retail Platinum;
- it looks intentional at iPhone emulator scale;
- it respects DS hardware/resource constraints;
- interaction state is obvious;
- the screen has stronger atmosphere or hierarchy than the Pass G baseline;
- it does not compromise gameplay readability;
- it builds on US Rev 0 and Rev 1.

The final target should feel like:

> **the strongest version of a DS-era Pokémon presentation, designed with modern visual priorities rather than 2009 retail conservatism.**
